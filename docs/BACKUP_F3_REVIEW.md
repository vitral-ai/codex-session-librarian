## Implemented behavior

`backup keys plan/apply/list` targets one existing local source, requiring explicit
selection if ambiguous. Plans bind old/new public recipients, profile/policy,
existing acceptance, producer fingerprint/config hash, source/set/repository IDs,
current set generation, complete/latest-source CPs, retained epoch dependencies
and random future profile epoch. A private reservation binds the entire canonical
plan. Changes require a new plan, including unrelated set-generation progress.
No private identity is read/generated by rotation; pinned age validates acceptance
of public recipients only. `keys list` is offline local metadata, not custody proof.

Apply uses the existing control CAS to bind an opaque crypto profile/epoch and
advance fencing generation. It then atomically installs the future config. Active
writers block rotation; expired actors lose their tokens. Old configs and pending
resumes cannot publish after rotation, including explicit new acquire. Producer
software upgrades can still create new versions within an unchanged key epoch.
The remote registry contains opaque IDs/hashes/operational dates, not public
recipients, keyring references, labels, ciphertext or conversation data.

Stable plan/result IDs reconcile accepted-write response loss, journal loss,
remote-commit/local-config failure and local-config/local-receipt failure without
a second rotation. Conflicting local edits remain intact; old plans cannot roll
back a later epoch. Existing config epoch maps are strictly validated, including
rejection of private/unknown fields. Stale plans use exit5 and failed attempts are
recorded before dependency resolution.

New fingerprints carry a validated `profile_epoch` UUID; the reader accepts
legacy fingerprints without it. Older strict F2 readers reject the new shape.
Physical containers stay schema1 and catalogs2. First post-rotation capture does
not require the new operational identity to decrypt the old catalog; a bound
source checkpoint boundary forces new future ciphertext instead. Old pointers
and bytes remain intact until a new complete pointer commits. Missing old local
sessions remain in old checkpoints/epochs, rather than falsely joining current
new-epoch coverage. Pointer key epoch is checked against the decrypted catalog.

The map records public recipient dependencies and known previous pointer UUIDs;
legacy mapping derives from config and is not a full historical audit. Operators
must retain external identities and verify retained checkpoints before retiring
operational identities. Removing a future recipient does not revoke old/downloaded
ciphertext. No integral/restored/native evidence is inherited by a new epoch.
Native+scrub remains rejected; portable scrub and accepted retain remain explicit.
